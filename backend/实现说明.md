# 后端实现说明

## 1. 应用入口（app.py）

### Flask 应用初始化流程

应用启动时依次完成以下步骤：

1. 创建 Flask 实例
2. 配置 CORS 跨域策略
3. 注册蓝图路由
4. 初始化日志系统
5. 注册全局错误处理器
6. 启动 HTTP 服务

### CORS 跨域配置

使用 `flask_cors` 扩展，配置如下：

```python
resources={r"/*": {
    "origins": "*",
    "methods": ["GET", "POST", "PUT", "DELETE", "OPTIONS"],
    "allow_headers": ["Content-Type", "Authorization"]
}}
```

允许所有来源访问，支持常见 HTTP 方法和请求头。

### 蓝图注册

所有蓝图统一挂载在 `/api` 前缀下：

| 蓝图 | 变量名 | 职责 |
|------|--------|------|
| health_bp | 健康检查蓝图 | 服务状态与系统设置 |
| api_mgmt_bp | API 管理蓝图 | API 配置与调用管理 |
| stream_bp | 流式通信蓝图 | SSE 流式响应 |
| prompt_bp | 提示词蓝图 | 提示词版本与模板管理 |
| chip_layout_bp | 芯片布局蓝图 | 网格配置 CRUD |

### 日志系统初始化

从 `config/settings.yaml` 的 `logging` 节读取配置：

- **level**：日志级别（DEBUG / INFO / WARNING / ERROR）
- **format**：日志格式字符串
- **file**：日志文件路径

使用 Python 标准库 `logging` 模块初始化，同时输出到控制台和文件。

### 全局错误处理器

注册两个 HTTP 错误处理器，统一返回 JSON 格式：

- **404 Not Found**：`{"code": 404, "message": "Resource not found"}`
- **500 Internal Server Error**：`{"code": 500, "message": "Internal server error"}`

### 启动参数

从 `settings.yaml` 读取 `server` 配置：

- `host`：监听地址
- `port`：监听端口
- `threaded=True`：启用多线程处理并发请求

### 根路由

`GET /` 返回服务运行状态信息，用于快速确认服务是否存活。

## 2. 控制器层设计

### base.py 基础设施

#### SSE_HEADERS 常量

为 SSE 流式响应定义的标准响应头集合：

```python
SSE_HEADERS = {
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache, no-store, must-revalidate",
    "X-Accel-Buffering": "no",
    "Connection": "keep-alive",
    "Access-Control-Allow-Origin": "*",
    "Access-Control-Allow-Headers": "Content-Type,Authorization",
    "Access-Control-Allow-Methods": "GET,POST,OPTIONS"
}
```

- `Content-Type: text/event-stream`：标识 SSE 协议
- `Cache-Control`：禁用所有缓存，确保实时性
- `X-Accel-Buffering: no`：禁用 Nginx 代理缓冲
- `Connection: keep-alive`：保持长连接
- CORS 头：允许跨域 SSE 连接

#### @error_handler 装饰器

统一异常捕获装饰器，包装控制器方法。当任何未处理异常抛出时，返回标准化 JSON 错误响应：

```json
{"code": 500, "message": "具体错误信息"}
```

### 各控制器职责

#### health_controller

- **健康检查**：返回服务运行状态、版本信息
- **系统设置获取**：返回当前系统配置摘要

#### api_controller

- **API 配置 CRUD**：增删改查 API 连接配置
- **密钥管理**：API Key 的安全存储与更新
- **模型列表**：获取指定 API 可用的模型列表
- **配置验证**：测试 API 连接是否可用
- **同步调用**：非流式 API 调用入口

#### stream_controller

- **SSE 流式通信**：支持两种模式
  - **两步式**：先创建会话，再通过 SSE 端点获取流式响应
  - **直接式**：单次请求直接返回 SSE 流
- **Agent Loop 工具调用循环**：支持 AI 自主调用工具的多轮循环
  - AI 返回 tool_calls → 执行工具 → 将结果注入上下文 → 再次调用 AI
  - 循环直到 AI 返回最终文本响应或达到最大轮次

#### prompt_controller

- **版本管理**：列出所有提示词版本
- **模块管理**：提示词模块的查看与编辑
- **模板渲染**：使用参数渲染提示词模板
- **搜索**：按关键词搜索提示词内容
- **统计**：提示词使用统计信息

#### chip_layout_controller

- **网格 CRUD**：芯片网格布局的增删改查
- **重置**：恢复为默认网格配置
- **统计**：网格配置统计信息（活跃电极数等）

## 3. 服务层设计与依赖注入

### 服务初始化链

服务实例按依赖顺序创建，采用手动依赖注入：

```python
config_service = ConfigService()
chip_layout_service = ChipLayoutService(config_service)
prompt_service = PromptService(config_service)
droplet_service = DropletToolService(config_service)
tool_registry = ToolRegistry(droplet_service)
api_service = ApiService(config_service, chip_layout_service, prompt_service)
```

依赖关系图：

```
ConfigService（基础配置）
    ├── ChipLayoutService（芯片布局）
    ├── PromptService（提示词管理）
    ├── DropletToolService（液滴串口通信）
    │       └── ToolRegistry（工具注册）
    └── ApiService（API 调用，依赖 ConfigService + ChipLayoutService + PromptService）
```

### 各服务职责

#### 1. ConfigService — 配置中心

YAML 配置文件统一加载与管理：

- **加载**：读取 `settings.yaml`、`api.yaml`、`prompt_config.yaml`
- **缓存**：内存缓存已加载的配置，TTL 为 3600 秒
- **热更新**：检测文件修改时间戳，自动失效缓存并重新加载

#### 2. ApiService — API 调用统一封装

核心枢纽服务，封装所有 AI API 调用逻辑：

- **客户端缓存**：同一 API 配置只创建一个 ApiClient 实例，避免重复初始化
- **速率限制检查**：基于配置的每分钟最大调用次数进行限流
- **提示词模板自动合并**：在调用 API 前，自动注入芯片布局信息到 system prompt
- **三种调用模式**：
  - `call_api()`：同步调用，等待完整响应
  - `stream_api()`：流式调用，逐块返回 SSE 事件
  - `agentic_stream_api()`：Agent Loop 模式，支持工具调用的多轮自动循环

#### 3. ApiClient（工厂模式）

基于 `api_type` 字段自动选择客户端实现，详见第 4 节。

#### 4. PromptService — 提示词版本化管理

- 加载 `config/prompts/v1/prompt_config.yaml` 中的提示词配置
- 支持模板渲染：使用 Python `.format(**params)` 替换占位符
- 版本管理与模块化组织

#### 5. ChipLayoutService — 芯片布局管理

- **常量定义**：`ROWS=17`、`COLS=22`、`MAX_VALUE=128`
- **配置优先级**：自定义配置（用户保存） > YAML 默认配置（prompt_config.yaml 中的 chip_layout.grid）
- **持久化**：写入 `data/chip_layout.json` 文件
- **验证规则**：
  - 行数必须为 ROWS（17）
  - 每行列数必须为 COLS（22）
  - 每个值必须在 0 ~ MAX_VALUE（128）范围内
- **`format_for_prompt()`**：将网格数据格式化为 LLM 可读的文本描述

#### 6. DropletToolService — 液滴串口通信

微流控芯片的物理控制服务，通过串口发送 29 字节帧协议驱动电极。支持 Mock 模式用于开发调试。详见第 6 节。

#### 7. ToolRegistry — 工具注册中心

- 管理 AI 可调用的工具定义
- 注册 `dispense_droplet` 工具（液滴分配）
- `execute_tool(tool_name, arguments)`：根据工具名称路由到对应服务执行

## 4. API 客户端工厂模式详解

### 类继承结构

```
BaseApiClient (ABC)
    ├── chat_completions(request) → ChatCompletionResponse
    ├── stream_chat_completions(request) → Generator
    └── get_models() → List[str]

OpenAIClient(BaseApiClient)   # DeepSeek / OpenAI 兼容
    └── 额外: chat_completions_with_tools(request)  # 返回含 tool_calls 的原始响应

QwenClient(BaseApiClient)     # 千问
    ├── _build_qwen_request(request)    # 请求格式转换
    └── _parse_qwen_response(data)      # 响应格式转换

ApiClientFactory
    └── create_client(api_type, config) → BaseApiClient
        ├── api_type='openai' → OpenAIClient
        └── api_type='qwen'   → QwenClient
```

### BaseApiClient 抽象基类

定义统一的客户端接口，所有具体实现必须覆写以下方法：

- `chat_completions(request)`：同步调用，返回 ChatCompletionResponse
- `stream_chat_completions(request)`：流式调用，返回 Generator 逐块产出
- `get_models()`：获取可用模型列表

### OpenAIClient

基于 `openai` SDK 实现，兼容所有 OpenAI 格式 API（包括 DeepSeek）：

- 使用 `openai.OpenAI(api_key, base_url)` 初始化客户端
- 流式响应直接使用 SDK 的 stream 迭代器
- **DeepSeek 特殊支持**：思维链（reasoning_content）字段解析
- **工具调用**：`chat_completions_with_tools()` 方法返回含 `tool_calls` 的原始响应对象，供 Agent Loop 使用

### QwenClient

基于 `requests` HTTP 库实现，适配千问 API 格式差异：

- `_build_qwen_request(request)`：将通用请求转换为千问 API 格式
- `_parse_qwen_response(data)`：将千问响应转换为统一格式
- **流式处理特殊逻辑**：千问 SSE 返回的是累积文本，QwenClient 内部计算增量差值，对外暴露增量输出

### ApiClientFactory

静态工厂类，根据 `api_type` 字段创建对应客户端：

```python
ApiClientFactory.create_client(api_type='openai', config={...})  # → OpenAIClient
ApiClientFactory.create_client(api_type='qwen', config={...})    # → QwenClient
```

## 5. 提示词模板渲染机制

### 模板位置

`config/prompts/v1/prompt_config.yaml`

### 占位符

| 占位符 | 数据来源 | 说明 |
|--------|----------|------|
| `{chip_layout}` | ChipLayoutService | 当前芯片布局的文本描述 |
| `{user_requirements}` | 用户输入 | 用户的实际需求文本 |

### 渲染流程

```
1. ApiService 加载 prompt_config.yaml 中的 prompt_template
       ↓
2. 从 ChipLayoutService 获取当前芯片布局数据
       ↓
3. 调用 format_for_prompt() 将布局矩阵格式化为 LLM 可读文本
       ↓
4. 替换模板中的 {chip_layout} 占位符
       ↓
5. 替换模板中的 {user_requirements} 为用户实际输入
       ↓
6. 将渲染后的完整文本作为 system prompt 发送给 AI 模型
```

渲染使用 Python 原生字符串格式化：

```python
rendered = template.format(chip_layout=layout_text, user_requirements=user_input)
```

## 6. 液滴工具串口协议

### 帧格式（29 字节）

| 偏移 | 长度 | 内容 | 说明 |
|------|------|------|------|
| 0-1 | 2 | 0xDD 0xD1 | 帧头，固定标识 |
| 2 | 1 | 0x18 | 数据区长度（24 字节） |
| 3 | 1 | OutputType | 输出类型标志 |
| 4-19 | 16 | 电极位图 | 128 个电极的开/关状态（每 bit 对应一个电极） |
| 20 | 1 | 电压码 | 驱动电压编码值 |
| 21 | 1 | AC 开关 | 交流信号开关（0=关，1=开） |
| 22-23 | 2 | 频率 | 大端序（Big-Endian）频率值 |
| 24-26 | 3 | 保留 | 预留字节，填充 0x00 |
| 27 | 1 | CRC | 校验和：`(长度 + sum(数据区)) & 0xFF` |
| 28 | 1 | 0x0A | 帧尾，固定标识 |

### 电极位图编码

16 字节（128 bit）表示 128 个电极的状态：

- 每个 bit 对应一个电极
- `1` = 电极激活（通电）
- `0` = 电极关闭

### CRC 校验算法

```python
crc = (data_length + sum(data_bytes)) & 0xFF
```

其中 `data_length` 为 0x18（24），`data_bytes` 为偏移 3~26 的 24 字节数据区。

### 工作模式

#### Mock 模式（`mock_mode: true`）

- 不打开物理串口
- 仅在内存中生成帧数据
- 输出日志记录帧内容，用于开发调试
- 默认启用，适用于无硬件环境

#### 真实模式（`mock_mode: false`）

- 通过 `pyserial` 库打开串口连接
- 串口参数从 `settings.yaml` 的 `serial` 节读取（端口号、波特率）
- 发送完整 29 字节帧到物理设备
- 需要确保串口号正确且设备已连接

## 7. 配置文件结构详解

### settings.yaml — 全局系统配置

```yaml
server:
  host: 0.0.0.0          # 监听地址
  port: 5000              # 监听端口
  debug: false            # 调试模式

config:
  cache_enabled: true     # 启用配置缓存
  cache_ttl: 3600         # 缓存有效期（秒）
  reload_interval: 60     # 配置重载检查间隔（秒）

logging:
  level: INFO             # 日志级别
  format: "%(asctime)s - %(name)s - %(levelname)s - %(message)s"
  file: logs/app.log      # 日志文件路径

api:
  timeout: 60             # API 调用总超时（秒）
  stream_timeout: 120     # 流式调用超时（秒）
  connect_timeout: 10     # 连接超时（秒）
  retry_count: 3          # 失败重试次数
  retry_delay: 1          # 重试间隔（秒）
  rate_limit: 100         # 每分钟最大调用次数

serial:
  port: COM6              # 串口端口号
  baud_rate: 115200       # 波特率
  mock_mode: true         # Mock 模式开关
```

### api.yaml — API 连接配置

```yaml
apis:
  qwen:
    name: qwen
    api_type: qwen                                    # 客户端类型 → QwenClient
    base_url: https://dashscope.aliyuncs.com/api/v1
    api_key: "your_key"
    auth_method: "bearer"
    default_model: "qwen-plus"
    models: [...]

  deepseek:
    name: deepseek
    api_type: openai                                  # 客户端类型 → OpenAIClient
    base_url: https://api.deepseek.com
    api_key: "your_key"
    default_model: "deepseek-v4-flash"
    models: [...]                                     # supports_thinking: true

global:
  timeout: 30             # 全局默认超时
  rate_limit: 100         # 全局默认速率限制
  default_api: "deepseek" # 默认使用的 API
```

`api_type` 字段决定 ApiClientFactory 创建哪种客户端实现。

### prompt_config.yaml — 提示词配置

```yaml
version: 1.3
description: "微流控液滴路径规划提示词"

chip_layout:
  grid: [[...], ...]      # 17×22 默认布局矩阵
  description: "..."      # 布局描述

prompt_template: |
  你是微流控液滴路径规划专家...

  ## 微流控芯片状态空间
  {chip_layout}

  ## 用户需求
  {user_requirements}
```

## 8. 日志系统

### 配置

| 配置项 | 来源 | 说明 |
|--------|------|------|
| 级别 | `settings.yaml` → `logging.level` | 支持 DEBUG、INFO、WARNING、ERROR |

```
2026-04-27 10:30:15,123 - api_service - INFO - API call to deepseek completed in 2.3s
```

- **droplet_tool_service**：串口帧发送、Mock 模式日志

## 9. 部署注意事项

### 生产环境配置

- 将 `settings.yaml` 中 `server.debug` 设为 `false`
- Flask 生产部署建议使用 **Gunicorn**（Linux）或 **Waitress**（Windows）替代内置开发服务器
- 配置文件缓存 TTL 默认 3600s，可根据需要调整

### 串口通信

- 生产环境需将 `serial.mock_mode` 设为 `false`
- 确保串口号正确：Windows 下为 `COMx` 格式
- 确保设备已连接且驱动已安装

### API 密钥配置

- 可直接在 `api.yaml` 中配置 `api_key`
- 也可通过 API 管理接口（api_controller）动态配置

### 前端部署

- 执行 `npm run build` 生成 `dist` 目录
- 将 `dist` 目录配置为静态文件服务（Nginx 或 Flask 静态文件托管）

### 权限要求

- 日志目录 `logs/` 需要确保写入权限
- 数据目录 `data/` 需要确保读写权限（芯片布局持久化）

## 10. 数据模型（api_utils.py）

### ChatCompletionRequest

API 调用的统一请求模型：

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| model | str | — | 模型名称（必填） |
| messages | List[Dict] | — | 消息列表（必填），格式 `[{"role": "...", "content": "..."}]` |
| max_tokens | int | 1024 | 最大生成 token 数 |
| temperature | float | 0.7 | 采样温度，越高越随机 |
| stream | bool | False | 是否启用流式输出 |
| top_p | float | 1.0 | 核采样参数 |
| thinking_enabled | bool | False | 是否启用思考模式（DeepSeek） |
| reasoning_effort | str | "high" | 思考强度：low / medium / high |
| tools | List[Dict] | None | 工具定义列表（Agent Loop 使用） |
| tool_choice | str | "auto" | 工具选择策略：auto / none / required |

### ChatCompletionResponse

API 调用的统一响应模型：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | str | 响应唯一标识 |
| object | str | 对象类型标识（如 `chat.completion`） |
| created | int | 响应创建的 Unix 时间戳 |
| model | str | 实际使用的模型名称 |
| choices | List[Dict] | 生成结果列表，每项含 `message`、`finish_reason` 等 |
| usage | Dict | token 使用统计：`prompt_tokens`、`completion_tokens`、`total_tokens` |
